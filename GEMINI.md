# Контекст проекта: Python REST API Service (Django)

## 🎯 Описание проекта
Бэкенд-сервис на Python, предоставляющий REST API для платформы объявлений с поддержкой чатов в реальном времени, фоновых задач, поиска и интеграции с Telegram.

## 🛠 Стек технологий
- **Фреймворк:** Django 5.0+ & Django REST Framework (DRF)
- **База данных:** PostgreSQL (Django ORM)
- **Real-time (WebSockets):** Django Channels + Daphne + Redis
- **Асинхронные задачи:** Celery + Redis / Flower
- **Поиск:** Elasticsearch (`django-elasticsearch-dsl`)
- **Документация API:** drf-spectacular (Swagger/OpenAPI)
- **Авторизация:** SimpleJWT (JWT) + Social OAuth2 + Password Reset
- **Качество кода и Стиль:** Ruff (стиль кода), Black (форматирование, длина строки 88), Mypy (строгая типизация Python 3.12).

## 📂 Архитектура и структура приложений (внутри src/)
- `config` — Основные настройки проекта, корневые URL-маршруты (`urls.py`) и конфигурация Celery (`celery.py`).
- `api` — Центральное приложение для версионирования и организации REST API (например, `v1`). Содержит логику авторизации, пагинации, пермишенов, валидаторов, схем, сериализаторов и представлений.
- `core` — Общие базовые модели, утилиты, константы, менеджеры, middleware и прочие вспомогательные функции, используемые во всем проекте.
- `ads` — Модуль для управления объявлениями.
- `bad_word_filter` — Модуль для фоновой модерации текстового контента, реализуемый через Celery-задачи (`tasks.py`).
- `categories` — Управление категориями для объявлений и услуг.
- `chat` — Функционал для чатов в реальном времени, включая WebSocket-логику (`consumers.py`).
- `comments` — Функционал для добавления и управления комментариями.
- `notifications` — Функционал для real-time уведомлений, включая WebSocket-логику (`consumers.py`).
- `services` — Модуль для управления услугами.
- `templates` — Общие шаблоны (например, для email-уведомлений).
- `users` — Управление пользовательскими аккаунтами, профилями, аутентификацией и авторизацией.

## 📜 Правила кодогенерации и взаимодействия (Компромисс: осторожность важнее скорости)

### 1. Думай перед написанием кода
Не строй догадок. Не скрывай непонимание. Выноси компромиссы на обсуждение.
Перед реализацией задачи:
- Явно сформулируй свои предположения. Если сомневаешься — спроси.
- Если есть несколько вариантов реализации, предложи их, а не выбирай один молча.
- Если существует более простое решение, сообщи об этом. Возражай разработчику, если это обосновано.
- Если что-то непонятно — остановись. Назови то, что вызывает путаницу, и задай вопрос.

### 2. Сначала простота
Пиши минимальный объем кода, который решает задачу. Никаких спекуляций.
- Не добавляй функции, о которых тебя не просили.
- Не создавай абстракций для кода однократного использования.
- Никакой «гибкости» или «настраиваемости» (конфигурации), если этого не требовали.
- Не пиши обработку ошибок для невозможных сценариев.
- Если ты пишешь 200 строк кода там, где можно обойтись 50, перепиши его.
- Спроси себя: «Сказал бы ведущий инженер (Senior), что это переусложнено?» Если да — упрощай.

### 3. Точечные (хирургические) изменения
Затрагивай только то, что необходимо. Убирай только свой мусор.
При редактировании существующего кода:
- Не «улучшай» соседний код, чужие комментарии или форматирование.
- Не проводи рефакторинг того, что работает исправно.
- Полностью подстраивайся под существующий стиль проекта (Ruff/Black), даже если сделал бы иначе.
- Если заметил несвязанный мертвый код, просто упомяни о нем, но не удаляй.
Когда твои изменения создают неиспользуемые элементы:
- Удаляй импорты, переменные и функции, которые стали ненужными именно из-за ТВОИХ правок.
- Не удаляй старый мертвый код, созданный до тебя, если об этом не просили.
*Критерий проверки:* Каждая измененная строка должна напрямую вести к запросу пользователя.

### 4. Целевое исполнение
Превращай задачи в проверяемые цели. Повторяй итерации до полной верификации.
Для многошаговых задач всегда пиши краткий пошаговый план реализации перед началом работы:
Строгие критерии успешности позволяют двигаться независимо. Слабые критерии («сделай, чтобы работало») требуют постоянных уточнений.

### 5. Специфика архитектуры Python и Django
- **Язык общения:** Всегда отвечай и пиши комментарии к коду на русском языке.
- **Типизация:** Пиши современный код на Python 3.12+. Всегда используй type hinting (указание типов для аргументов и возвращаемых значений функций и методов) в соответствии с правилами `Mypy`.
- **Стиль кода:** Пиши код, строго соответствующий правилам `Ruff` и `Black` (используй двойные кавычки `"`, длина строки до 88 символов). Не генерируй docstrings (строки документации), если линтер Ruff их игнорирует по текущим правилам проекта.
- **Архитектура Django:** При создании API используй сериализаторы DRF (`serializers.Serializer` / `ModelSerializer`) и ViewSets (`viewsets.ModelViewSet` или Generic Views). Соблюдай тонкие view и толстые модели/сервисы.
- **Фоновые задачи:** При необходимости выноса тяжелой логики (отправка писем, уведомлений, синхронизация с Elasticsearch, модерация) создавай асинхронные Celery-таски (`@shared_task`) в файлах `tasks.py`.
